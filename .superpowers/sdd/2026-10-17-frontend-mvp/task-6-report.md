# Task 6 report — Flutter progress, nutrition and privacy

## Implementation and contract decisions

- Read the exact Task 6 brief, product spec, Flutter 03/04 prompts, Task 5 source/interfaces/report and actual backend assessment/nutrition/food/core/user serializers, views, models, comparison and composition services. Visually inspected approved mobile boards 03, 05 and 06. Checked consumed routes against `/tmp/bota-o-shape-openapi.yaml`.
- Replaced the student shell's progress/nutrition placeholders and profile implementation with focused feature pages using the existing Material theme, shared cards, scrollable bodies, student-only navigation and large-text preferences. Existing workout history remains available through Progresso and Treinos; it retains Task 5's real-session period filter without inventing planned dates.
- Progress lists only this student's released assessments. Metric/method selection and interval filters feed a bar visualization with numeric dates/units and a textual table. Missing/incompatible samples remain gaps, never zero or interpolated points. Comparison requires identical metric, unit, method, protocol, point, side, origin, equation metadata, device and preparation conditions. Reports display raw values, method/protocol, conditions, device, equation/applicability, professional notes, signed changes and percentages, with a zero baseline yielding no percent. Direction uses neutral increased/decreased/unchanged text. Reports are fetched only after validating the assessment is own/released, then checked for `released_to_student` and matching assessment ID.
- The assessment serializer excludes evaluator identity. The report honestly states the evaluator is unavailable; it never infers a name. Photos have no exposed read/upload contract and no photograph is fabricated, fetched or shared. The interface explains private/consented use rather than introducing an unsupported photo flow.
- Nutrition displays the assigned published plan's CRN/UF, version, publication date, review date, period, objective/change summary, meal times, food quantities/units/grams, preparation, observations and only provided authorized substitutions. Paused/unpublished/not-yet-started/expired plans cannot receive a check-in. Offline copies are explicitly opened, timestamped and marked possibly stale; check-ins are disabled from that view and revalidate the live plan/version/slot at dispatch.
- The student plan serializer omits author name/ID and planned-food nutrition snapshots. UI identifies missing authorship/composition honestly and directs the student to the academy. There is no invented professional identity, author lookup or locally prescribed target. `MealSlot.day` is an unconstrained positive integer without a documented weekday mapping: the selector shows **Dia 1 / Dia 2 / …**, rather than inventing a calendar correspondence.
- Optional meal check-ins use **Segui / Segui parcialmente / Não segui**, with separate note/question fields and no score, blame or streak. Ad-hoc meals and hydration are explicitly student diary records, separated from prescribed foods. They have selectable date/time, optional portion/observation, empty/loading/error states, and owned-record edit/delete actions through the real PATCH/DELETE endpoints with explicit deletion confirmation. Nutrition messages are private by default (`shared_with_coach: false`).
- TBCA is the default catalog source, with USDA FoodData Central as an explicit complementary source. Results preserve preparation, generic/branded distinction and source/version. The app uses the imported food catalog and its real per-food calculation action to obtain the nutrient basis per 100 g; no client USDA secret or hypothetical TBCA API is introduced. The backend external USDA search only supplies metadata, so the app does not treat external results as imported foods with usable nutrient data.
- Positive grams recalculate the six supported MVP nutrient fields proportionally. Household selection is offered only for that food's documented gram conversion with evidence. Missing nutrients remain unknown, including totals when any included item lacks a value. Unsupported micronutrients are preserved in the original snapshot but not mislabeled with inferred units in meal/day summaries. A multiple-food ad-hoc meal has a descriptive total; because the API stores one food per MealLog, it creates independent local intents per item with a common descriptive meal title/time, not a fabricated atomic meal endpoint. The user reviews/sends each saved item explicitly.
- Nutrition intent UUIDs, chosen source/version/nutrient snapshots, plan copies and privacy drafts use the existing encrypted `PrivateStore` in real mode, scoped by API origin, tenant and student. Demo data is a separate explicit gateway with fictitious labels and memory storage; API failures never switch to demo. Successful diary reads are not recalculated against today's catalog. Because the API omits historical diary nutrition snapshots, unknown remote/other-device composition remains unavailable; it is not silently regenerated. Before dispatching a catalog diary record the app reconfirms its source/version/preparation/per-100-g data, blocking a changed composition until the student selects it again.
- **No nutrition idempotency contract:** each intent is durably written before dispatch, with a local UUID that is never sent as a nonexistent backend idempotency field. There is no automatic nutrition replay. Transport loss, malformed success, server error or interrupted `sending` state requires explicit reconciliation. On restart, interrupted sends become uncertain. The student must consult fresh server records and identify the received record or explicitly confirm absence; that action merely prepares a draft, and another explicit action sends it. Rejected writes are preserved for review. Unsubmitted forms and the multiple-food composer confirm before discarding unsaved data. A partial local composer save removes only durably saved items, so a subsequent save does not create duplicate local intents.
- Added the backend-required `nutrition_plan` consent as an independent initially-off purpose. Existing local preferences merge new purpose keys without implicitly granting them; explicit revocation still targets only the appropriate server record. Profile reuses the existing consent/preference flow, academy switching and logout. It prepares an encrypted local export/deletion request draft and explains secure contact/identity/retention steps through the academy. No export/deletion endpoint exists: the app never claims a request was sent, data exported or the account deleted. Logout ends authentication while retaining isolated encrypted pending records under Task 5's policy.
- No billing, streaks, automatic goals, clinical advice, barcode, camera or wearable integration was added. No dependencies or abstractions beyond the focused repository/models/pages were introduced. Untracked `docs/reference/` and `docs/superpowers/sdd/` were not edited, staged or deleted. No subagents were dispatched.
